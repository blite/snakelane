    Design notes: project, App Store Connect, listing¶

    These are the reasons behind decisions in the code for the project, App Store Connect and listing modules, moved out of comments.

    Project and config¶

    Find the repo from the working directory¶

    The scripts used to live in each app's Metadata/scripts/ and found everything relative to their own file. Installed once and shared, snakelane finds the repo relative to where it is run instead. It walks up from the working directory to the first folder holding a config, the way git finds .git. -C <dir> and --config <file> override the walk. Xcode doesn't run the post-action from the project folder, so the post-action changes to $PROJECT_DIR first, and bump falls back to $PROJECT_DIR and $SRCROOT, which Xcode sets.

    Root YAML configs replaced app.json¶

    Until 2026-10-02 each app was configured by Metadata/<App>/app.json. The config moved to snakelane.yml (or snakelane.<name>.yml) at the repo root. A repo with one app has no extra folder level, a config can carry comments, and the metadata folder is wherever the repo wants it. --app matches names and aliases case-insensitively, because typing a name after reading a directory listing should not be a wrong guess. With several apps, an unnamed or unknown --app fails rather than picking one.

    Decimals stay text in YAML¶

    Configs are read with YAML 1.2 rules, so only true and false are booleans. NO (Norway), yes and on stay strings. snakelane adds one rule of its own: decimals are kept as their text. A price of 9.90 stays "9.90", not the float 9.9, and a version 1.10 stays "1.10". These files hold far more prices and versions than real fractions, so the few numeric settings (a framing bias, a settle time) are converted where they are used.

    Raw captures live outside metadata/¶

    Raw captures moved from metadata/ to .snakelane/<slug>/raw/ on 2026-10-02. They are regenerated by every shoot and were gitignored in most apps. metadata/ is now only what you edit and what ships.

    The default platform is iOS¶

    When --platform is omitted it is ios if the app ships iOS, otherwise the app's only platform. Every app shipped iOS when the platform was hardcoded, and a Mac-only app should not need --platform macos on every command.

    App Store Connect client¶

    Credentials are files at fixed paths¶

    Before snakelane, the key came from three APP_STORE_CONNECT_API_KEY_* environment variables. An Xcode launched from the Dock never sees a shell's variables, so the Archive post-action quietly skipped its TestFlight check on exactly the archives it exists for. Both credential paths now hang off $HOME alone, which every process has, so a terminal, an Xcode post-action and CI read the same key. XDG_CONFIG_HOME is not honoured for the same reason: a variable set in a shell profile would split the CLI and Xcode onto two different files.

    The key lives in ~/.appstoreconnect/private_keys/AuthKey_<key_id>.p8 because altool will not take a path to a .p8. It searches fixed directories for that file name, and this is one of them, so xcodebuild, altool and the client share one copy. The Keychain was ruled out because xcodebuild -exportArchive and altool both need the key as a file, so it would be written back to disk on every upload.

    auth setup moves the key and never overwrites one¶

    Apple lets you download a .p8 exactly once, so the copy in ~/Downloads is usually the only one, and a second copy left lying around is how keys leak. setup therefore moves the key rather than copying it, into a 0700 directory with mode 0600. It never overwrites a different existing key, because losing the only copy means revoking it. The file must parse as an EC private key before anything moves, so a truncated paste fails at setup rather than as an opaque 401 mid-upload. --key - reads stdin so CI can install from a secret without a temporary file. check warns about a key inside a git work tree because a dotfiles repo rooted at $HOME would publish it.

    ASC errors carry the HTTP status¶

    ASCError keeps Apple's status and error codes so a caller can tell "this resource doesn't exist" (404) from "the read failed". That is the difference between creating something and refusing to guess. On 2026-10-02 a timed-out read of a subscription's price was taken as "unpriced" and the price was written again. Apple's payloads also bury the useful sentence under errors[].detail, so the client surfaces it verbatim instead of a bare 409. A network failure is a separate TransientNetworkError: nothing was learned, so after a write the live state is unknown.

    Only GETs are retried¶

    Retries use urllib3's Retry on the session adapter (2026-10-02; this was a hand-written loop). Only GET and HEAD are retried once sent: a write that timed out may have been applied, and repeating it could create a second permanent product. urllib3's default would also retry PUT and DELETE. A DELETE that landed answers 404 the second time, which would read as a failure of something that succeeded. Any request is retried if it never connected, since nothing reached Apple. 429 and 5xx are retried for GETs, honouring Retry-After: a GET can answer 500 twice and 200 on the third try, and treating that as fatal once turned a status poll into a dead catalogue push.

    The dry run is the client's¶

    Until 2026-10-02 each write site checked --dry-run itself and printed its own "would …" line: two dozen branches across iap push, subs push and the screenshot and preview pushes, and a site that forgot one would have written to App Store Connect during a dry run. Now asc.Client(dry_run=True) reads as usual and never writes. Each POST, PATCH, DELETE and upload part is printed with its path and attributes. A create answers with a planned-N id, and reads under that id come back empty, so the rest of the push runs on as it would after a real create. A new product's localizations, availability and review screenshot all appear in the plan, where the old dry runs stopped at the product. The one place that still asks is the price lookup: a planned product has no price points to read. Result lines go through client.report, which a dry run silences, so nothing claims a write happened. tests/test_dry_run.py runs every push against a local server and fails if anything but a GET arrives.

    Find the app by exact bundle id¶

    Apple's filter[bundleId] is a prefix match. Querying com.example.Game also returned com.example.GamePlus, and taking the first result once pointed a freemium push at the paid app's listing. Only an app-name-already-taken 409 stopped it writing. The filter narrows and the client compares exactly. When snakelane.yml carries apple_id, resolving to any other app is an error. An empty apple_id means the record does not exist yet, not an id nothing can match.

    An upload is done when Apple has processed it¶

    The final PATCH of an upload only acknowledges receipt. assetDeliveryState then moves to COMPLETE, or to FAILED with a reason such as wrong dimensions or a corrupt file. fastlane's deliver waited on this state, and finishing without the wait reports success for screenshots Apple then quietly drops.

    A failed processing poll counts as timed out¶

    While waiting on processing, any failure to read the status means the answer is unknown, which is what "timed out" already means to every caller. This includes a 500 that outlives the client's retries, not only network errors. Treating it as fatal would take down a catalogue-wide push and abandon dozens of unprocessed products over a status check.

    Listing¶

    Blank local text means no opinion¶

    App Store Connect has no notion of "leave this alone", so writing an empty string would clobber whatever is live. A missing or blank file means the field is skipped. The same holds for the App Review card and for store pull, which never writes an empty file.

    The listing is written once, platforms override¶

    Until 2026-10-02 every iOS and Mac app duplicated its whole listing per platform, byte for byte in all five. Now the listing lives once in metadata/ and a platform folder holds only what differs, such as a Mac description. App-level fields (name, subtitle, the privacy URLs) are one per locale at App Store Connect, so a platform copy is refused; otherwise the last platform pushed would win.

    store is one command from ten copies¶

    store used to be ten drifting copies of Metadata/scripts/store.py, one per app repo. It is the union of them, with every fix any copy carried and nothing app-specific left in the code. Until 2026-10-02 it was one 3,500-line module; it is now only the command line, routing to listing/, screenshots/ and purchases/. It calls the REST API directly, so a failure names the resource and attribute instead of surfacing through fastlane's layers.

    Category relationship names¶

    The sub-category relationships are primarySubcategoryOne and so on, not primaryCategoryOne. The first push used the latter and App Store Connect answered with a 409 naming each one an "unknown relationship", which the old warn-and-continue handling buried as "often safe to ignore". The per-repo show commands had the same mistake and always printed None for every sub-category. APP_CATEGORIES is a snapshot from 2026-10-02 for catching typos in offline dry runs; a real push checks the live list so a new category is never refused.

    Age rating keys are not hardcoded¶

    The config's age_rating block uses snake_case versions of Apple's attribute names. Apple rewrote the questionnaire in 2025 and will again, so the keys are not listed in code. A real push checks them against the live declaration before writing anything, and patches only the changed answers because Apple refuses a PATCH whose every attribute already matches.

    Limits are checked before any network call¶

    Apple's per-field character limits are enforced locally, so a too-long field fails in the plan stage, dry run included. Otherwise it fails as a 409 halfway through a push that has already written half the listing, as in "Promotional text cannot be longer than 170 characters."

    Refused characters in listing text¶

    App Store Connect refused release notes for 1.2 with a 409 mid-push: "What's New in This Version can't contain the following character(s): ✓." Apple does not publish the list, so snakelane blocks the ranges that trip it, Dingbats and emoji. It leaves alone symbols that have been accepted in these files, such as • × — « » ° and accented letters.

    The review detail is created on first push¶

    Apple never creates a version's appStoreReviewDetail on a fresh app; fetching it 404s until the web UI saves the version or someone POSTs the record. The old Fastfile carried an ensure_app_store_review_detail_exists helper because deliver probed the resource and crashed on the 404. snakelane creates it on the first push, so the probe and the fix are the same code path. The create sends the full card, not just the changed fields, or the rest would be dropped.

    A push is verified by reading it back¶

    After writing, store push reads App Store Connect again and compares. A mismatch means Apple accepted the write but stored something different, through normalisation, silent truncation or a race with the web UI. That drift otherwise goes unnoticed until review, so a mismatch exits non-zero for CI and agents.

    Lint matching rules¶

    A listing rejection costs a review round trip, usually a day, and most causes are mechanically detectable. Phrases are bounded by Latin letters, not regex \b: "androgynous" does not match "Android", but "Androidにも対応" does, where \b would miss every unspaced script. The rule list came from storescreens-cli's precheck (2026-10-02). Placeholders are case-sensitive: "TODO" in capitals is a placeholder, "todo" is a to-do app describing itself. Outside English only the note form ("TODO:") counts, because PoolLog's es-ES description heads a section "TODO LO QUE INCLUYE". lint.ignore exists because a heuristic must never force a code change.

    Translation tracking¶

    snakelane does not translate; the agent operating it does. It keeps the record a person never keeps by hand: what source text each translation was made from, and whether anyone has reviewed it since. Editing a translation by hand after marking counts as review, an idea from storescreens-cli's translate manifest (2026-10-02). Locales that inherit the default text are counted, not flagged, since en-AU showing en-US copy is a choice. Platform overrides are not tracked: they are rare, and their source is whatever the platform would otherwise show.
